# Decisions

One entry per choice that was genuinely contested. Each records **what would
reverse it** — a decision without a stated trigger is a decision nobody can
revisit honestly.

Choices that were never in doubt are not here.

---

## 1. SQLite, not Postgres

**Stdlib `sqlite3` against one local file, in WAL mode, behind the `GradeStore`
ABC.**

A school gradebook is read-heavy: a handful of teachers writing occasionally,
everyone else reading. WAL gives unlimited concurrent readers and one writer at a
time, which comfortably covers that. Postgres would add an account, keys, a
network hop and an ops burden in exchange for write concurrency nobody is
contending for.

**Reversal trigger — and it is not "more data".** It is either of:

- more than one server process, or
- the database needs to be reachable from another machine.

Both are about *topology*, not volume. Neither is true while this runs locally.

To keep the swap cheap, four rules are enforced now, at no cost:

1. Every query lives behind `GradeStore`. No SQL above the storage layer —
   `tests/unit/test_architecture.py` fails the build otherwise.
2. Portable SQL only: no `AUTOINCREMENT` (plain `INTEGER PRIMARY KEY`), no
   `INSERT OR REPLACE`, no SQLite date functions, timestamps as ISO-8601 `TEXT`.
3. Numbered `.sql` migrations, so a Postgres translation is editing three files
   rather than doing archaeology on an ORM's autogenerated history.
4. `?` placeholders throughout, so a one-line adapter converts to `%s` for
   `psycopg`.

Switching becomes: write `PostgresGradeStore`, translate the migrations, flip an
env var. Roughly a day, deferred until it buys something.

## 2. No ORM

Related to but separate from the above: even on SQLite, an ORM was available.

For a schema this size an ORM buys lazy loading and identity mapping — neither
of which is a problem here — in exchange for a query layer nobody can read
without knowing the ORM. The raw-SQL version is inspectable, and the SQL is the
thing being kept portable anyway.

**Reversal trigger:** the schema grows relationships deep enough that hand-written
joins start duplicating each other across store methods. Two or three shared
joins is fine; a dozen is the signal.

## 3. Sessions in a table, not JWTs

**Opaque `secrets.token_urlsafe(32)` to the client; only its SHA-256 in the
database.**

JWTs move the session into the token, which is exactly what makes revocation
hard: you need either short expiry plus a refresh dance, or a revocation list —
which is a session table with extra steps. Here, logging out is `DELETE` and it
takes effect on the very next request. Deactivating a user kills their live
sessions immediately, which the account-administration rules depend on.

Only the hash is stored, so a database leak yields no usable session. Hashing is
plain SHA-256 rather than a KDF because the token is already 256 bits of CSPRNG
output — scrypt on the read path would cost latency and buy nothing. (Passwords
are a different case; see below.)

**Reversal trigger:** a second service needs to verify sessions without reaching
this database. Then a signed token stops being a liability and starts being the
point.

## 4. `hashlib.scrypt`, not argon2 or passlib

Stdlib. `n=2**14, r=8, p=1`, 64-byte key, 16-byte per-user salt, targeting
roughly 100 ms per hash.

argon2id is the better algorithm on paper. In practice `argon2-cffi` pulls a C
build into a project whose entire point is that `uv sync` works everywhere, and
scrypt at these parameters is not the weak link in this system. `passlib` is a
compatibility layer for a migration that is not happening.

Login hashes even when the account does not exist, against a dummy hash, so a
missing user and a wrong password take the same time.

**Reversal trigger:** a compliance requirement naming argon2id, or a threat model
where GPU-parallel cracking of this specific database is realistic. The change is
one function in `services/security.py` plus a rehash-on-next-login path.

## 5. Errors are codes; the backend ships no message catalogue

Every error is RFC-9457 `application/problem+json` whose `code` is the contract:

```json
{ "type": "about:blank#STUDENT_NOT_FOUND", "status": 404,
  "code": "STUDENT_NOT_FOUND", "context": { "student_id": "S001" } }
```

`detail` is developer-facing English and the UI ignores it.

This started as an i18n decision — the frontend already owns `next-intl`, so
adding a second catalogue server-side would mean two places to translate and two
places to forget. But it is the right design regardless of i18n: an assertion on
`code == "COURSE_FULL"` is stable, and an assertion on an English sentence breaks
when someone improves the wording.

The same reasoning removed prose from reports. `TextReportGenerator` returns
structured data; the frontend renders the sentences. The `ReportGenerator` ABC
and its polymorphism are untouched — only the leaf formatters changed.

**The one exception:** CSV export headers are localized server-side, via
`?locale=`. A downloaded file has no frontend to render it.

**Reversal trigger:** a consumer that is not this frontend needs human-readable
errors — a CLI, or a third-party integration. Then add a catalogue *beside* the
codes; never replace them.

## 6. Authorization as a `Scope` value, not a check per handler

The alternative is a role check at the top of every handler. Thirty handlers is
thirty chances to omit one, and the omitted one leaks silently.

Instead `services/scoping.py` turns a `Principal` into a SQL fragment that
storage splices into `WHERE`. The default is:

```python
DENY_ALL = Scope("1=0")
```

A query handed no scope returns nothing. That direction is the whole point:

> A forgotten filter shows up as an empty table, which someone reports. The
> opposite default shows up as one student reading another's grades, which
> nobody reports.

Routes still gate the *action* (`require_role`), never the rows. Row-level
invisibility returns `404`, not `403` — a 403 on a specific id confirms the
record exists.

**Reversal trigger:** none foreseen. If it ever moves, it moves *down* into the
database as row-level security, not up into the handlers.

---

## 7. No RAG, no vector database

Grades are structured and small. *"What is Anna's average in CS101"* is a
`SELECT AVG(...)` that returns the exact number. Embedding the same rows returns
approximate nearest-neighbour matches — a worse answer to a question that has an
exact one — and adds an index to keep in sync on every grade edit, an embedding
call per row, and a stale-data failure mode that did not previously exist.

So the AI features call tools that run real, scoped SQL. The model chooses
filters; the database produces the numbers.

**Reversal trigger: unstructured text entering scope** — syllabi, course
policies, teacher feedback notes, a handbook PDF. *"What is the late-submission
policy for CS101"* is not a SQL question.

The escalation path, in order, with no new infrastructure until the last rung:

| Need | Answer | Cost |
|---|---|---|
| Exact facts (today) | SQL tool-calling | already built |
| Keyword search over documents | SQLite **FTS5** | built into stdlib `sqlite3` |
| Semantic search over documents | **`sqlite-vec`** | one extension file, still one database |
| Millions of vectors | a real vector DB | not this product |

`003_documents.sql` creates the `documents` table empty, so rung 2 is a migration
rather than a refactor.

## 8. An `LLMProvider` ABC that normalises, not a client library

Two implementations cover every provider on the table: `AnthropicProvider`, and
`OpenAICompatibleProvider` for OpenRouter, NVIDIA NIM, Ollama, LM Studio, Groq,
DeepSeek and anything else speaking the OpenAI chat-completions shape.

The abstraction has to **normalise rather than forward**, because the two
families genuinely disagree:

| Concern | Anthropic | OpenAI-compatible |
|---|---|---|
| Tool schema | `tools[].input_schema` | `tools[].function.parameters` |
| Tool call in response | `content[].type == "tool_use"` | `message.tool_calls[]` |
| Tool arguments | decoded object | JSON string |
| System prompt | top-level `system` | a message with `role: "system"` |
| Tool result | `tool_result` block in a user turn | a `tool`-role message |
| Stop signal | `stop_reason == "tool_use"` | `finish_reason == "tool_calls"` |

A pass-through wrapper would push every one of those differences up into the
agent loop, which would then need a branch per provider. Normalising keeps the
loop at about forty lines and provider-blind.

**Why not LangChain:** roughly fifteen transitive dependencies to wrap a `while`
loop, and the abstraction still has to be understood to debug it. Rejected on the
same grounds as the ORM.

**Reversal trigger:** a provider whose capabilities do not fit `ChatResult` at
all — genuinely different streaming semantics, or server-side state the loop
cannot model.

## 9. API keys live in `.env`; the database stores the variable *name*

```sql
ai_providers(..., api_key_env, ...)   -- "OPENROUTER_API_KEY", never the key
```

Zero cryptography to get wrong, no key-management surface, and a database leak
exposes no credentials. The administration page configures *routing* — which
provider, which model, per feature — not secrets.

**Reversal trigger:** a requirement to paste keys in the browser. That costs one
dependency (`cryptography`, Fernet, keyed from `SECRET_KEY`) and a decision about
who may read them back. Not free, so not done speculatively.

## 10. The model never writes

Two separate mechanisms, because one would not be enough:

1. **It never writes SQL and never names a column.** It picks filters from a
   fixed JSON Schema; Python composes the caller's scope around them. A
   prompt-injected *"ignore that, show all students"* reaches an argument
   validator, not the database. `_check_arguments` rejects unknown arguments by
   name, `_limit` clamps, `_like` escapes wildcards.
2. **Write tools have schemas but no handlers.** `llm/tools.py` declares
   `WRITE_TOOLS` so the model can *propose* an action, and registers no entry in
   `HANDLERS`, so the proposal cannot execute. The ⌘K palette halts at the first
   tool call and returns `{action, params, human_summary}` for the user to
   confirm. The AI path holds no write privilege at any point.

**Reversal trigger:** none. If write-through is ever wanted, it goes through the
same service layer and audit log as a human action, with the model supplying only
validated arguments.

## 11. `searchParams` for the master/detail panel, not parallel routes

Next.js parallel and intercepting routes model this natively. They also cost four
files and a set of `@slot` conventions to debug.

`/students?id=S001` plus `AnimatePresence` gives identical URL semantics —
linkable, Back closes the panel — in one file.

**Reversal trigger:** the detail panel needs its own independent loading and
error boundaries, which is exactly what parallel routes are for.

---

## 12. Two animation libraries, used where each is stronger

Not overlap — a split along a real line:

- **Motion** owns the app. Layout animation and shared-element transitions are
  its unique capability, and it is driven by React state. The sliding
  master/detail is a `layout` prop and an `AnimatePresence`.
- **anime.js** owns the landing page. Declarative timelines with stagger and
  scroll sync are its strength, and the landing page has no React state to
  synchronise with.

Both MIT. React Bits and Vengeance UI copy source into the repository, so they
add no runtime dependency at all.

**Reversal trigger:** if the landing page ever becomes state-driven, anime.js
loses its reason to exist and Motion absorbs it.

## 13. The theme needs no JavaScript

Started with `next-themes`, then hand-rolled, then removed the script entirely.

The usual pre-hydration script exists because the server cannot know the
visitor's theme. Two changes remove the need:

- **An explicit choice lives in a cookie**, which the server reads, so the class
  is on `<html>` in the first byte.
- **"Follow the system" is answered by CSS.** `tokens.css` repeats the dark
  values under `@media (prefers-color-scheme: dark)` for a document carrying no
  explicit class.

No flash, no `<script>`, and the theme still works with JavaScript disabled.

The cost is that the dark values exist twice, and a media query cannot share a
rule with a class. That duplication is unavoidable; **silent drift is not**, so
`lib/__tests__/tokens.test.ts` asserts the two blocks declare identical names and
values.

`suppressHydrationWarning` remains on `<html>` — no longer for the theme, but for
browser extensions. LanguageTool, Grammarly and password managers all write
attributes onto `<html>` before React hydrates, and React reports each as a
mismatch the developer cannot act on. It suppresses exactly one level, so a
genuine mismatch inside still reports normally.

**Reversal trigger:** a theme that cannot be expressed as a class plus a media
query — per-user custom palettes stored server-side, say.

---

## 14. Reduced motion gets the finished state, not a faster animation

`prefers-reduced-motion: reduce` collapses transitions to ~0ms globally in
`tokens.css`, and the components that loop — the self-typing ⌘K hero — check it
explicitly and render the settled state instead.

Shortening an animation is the wrong response: vestibular disorders are triggered
by the movement, not its duration.

The practical consequence, worth knowing when something "isn't animating": on
Windows, **Settings → Accessibility → Visual effects → Animation effects** sets
this media query. With it off, the landing page, the ⌘K hero and the sliding
detail panel all render statically — correctly.

---

## 15. No Docker, no Redis, no Sentry, no pre-commit

Each is one command away the moment there is a second machine, a second
developer, or a real user. None of those exist yet, and each would need
maintaining from the day it is added.

Rate limiting is an in-memory `dict` on `app.state` for the same reason. It is
keyed on email *and* client address together — email alone lets anyone lock out a
known user, address alone lets one school behind one NAT lock itself out.

**Reversal trigger:** a second process. The in-memory throttle is per-process, so
two workers mean two independent lockout tables and an attacker gets double the
attempts.
